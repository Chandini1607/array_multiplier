# 4-Bit Unsigned Registered Array Multiplier --- RTL to GDSII

## Project Overview

This project implements a **4-bit unsigned array multiplier** in Verilog
and takes it through a digital ASIC implementation flow:

1.  RTL design
2.  Functional simulation
3.  Waveform inspection
4.  Logic synthesis
5.  Static timing analysis (STA)
6.  Physical design using LibreLane/OpenROAD
7.  DRC/LVS checks and final GDSII generation

The top-level design is named `mult_array`. It accepts two 4-bit
unsigned operands, `a` and `b`, and produces an 8-bit product, `p`.

## Design Specification

### Top-level module

``` verilog
mult_array (
    input        clk,
    input        rst_n,
    input  [3:0] a,
    input  [3:0] b,
    output [7:0] p
);
```

The actual module declaration in `rtl/mult_array.v` is authoritative if
it differs from this summary.

  Signal    Direction      Width Description
  --------- ----------- -------- -------------------------------
  `clk`     Input          1 bit Clock
  `rst_n`   Input          1 bit Asynchronous active-low reset
  `a`       Input         4 bits First unsigned operand
  `b`       Input         4 bits Second unsigned operand
  `p`       Output        8 bits Product of the operands

### Arithmetic range

For unsigned 4-bit operands:

-   Each input represents a value from 0 through 15.
-   The output represents a value from 0 through 225.
-   The product requires 8 bits because (15 `\times 15`{=tex} = 225).

### Architecture

The design is an array multiplier built from partial products and
full-adder logic. The design files include:

-   `rtl/mult_array.v` --- top-level multiplier RTL.
-   `rtl/full_adder.v` --- full-adder building block.

The design implementation discussed during this project uses registered
inputs/output and an asynchronous active-low reset. The recorded design
notes indicate a two-cycle latency; verify the exact cycle-by-cycle
behavior in `rtl/mult_array.v` and the testbench before describing it as
a guaranteed interface contract.

## Running the RTL Simulation

Run these commands from the project root,
`/foss/designs/array_multiplier`, inside the Linux container.

### 1. Compile the testbench and RTL

``` bash
iverilog -g2012 -o sim tb/tb_mult.v rtl/full_adder.v rtl/mult_array.v
```

This compiles the testbench and the two RTL source files into the
simulation executable named `sim`.

### 2. Run the testbench

``` bash
vvp sim
```

**Recorded result:** the testbench reported:

``` text
PASS: 256 vectors checked, 0 errors
```

The simulation reached `$finish` after the testbench completed. This is
evidence that the tested input vectors passed the testbench's checks. It
does not, by itself, prove physical timing closure or silicon
correctness.

### 3. View the waveform

The testbench writes `mult.vcd`. Open it with:

``` bash
gtkwave mult.vcd
```

If GTKWave is running in the Docker container's graphical desktop and
reports that it cannot initialize GTK or cannot find a display, first
confirm that the noVNC desktop is available. In the environment used for
this project, the display socket was `/tmp/.X11-unix/X1`; the following
worked for launching the GUI in that session:

``` bash
export DISPLAY=:1
gtkwave mult.vcd
```

In GTKWave, useful signals include `a`, `b`, `p`, `clk`, `rst_n`,
`expected`, `checked`, and `errors`. Inspect multiple operand
combinations, including non-zero values, and compare `p` with the
expected product after accounting for the design's register latency.

## Logic Synthesis

Run from the project root:

``` bash
yosys -c synth/synth.tcl
```

The synthesis script reads the RTL, elaborates the design, maps logic to
the selected standard-cell library, and writes the generated netlist and
statistics under `synth/`.

Expected output files:

-   `synth/mult_array_netlist.v`
-   `synth/mult_array_stat.rpt`

The observed synthesis statistics included a mapped cell breakdown and a
reported module area of approximately `746.966` in the units used by
that synthesis report. **Do not compare this number directly with the
final physical-design core area**: they are different metrics and may
use different units or account for different structures.

To inspect the generated files:

``` bash
ls -lh synth/
cat synth/mult_array_stat.rpt
```

## Static Timing Analysis (STA)

Run from the project root:

``` bash
sta sta/sta.tcl
```

The STA script loads the synthesized netlist, timing library, and timing
constraints, then reports timing paths and slack.

The project contains these timing reports:

-   `sta/mult_array_timing.rpt`
-   `sta/mult_array_timing_10ns.rpt`
-   `sta/mult_array_timing_2p60ns.rpt`

A report inspected during the project showed positive slack values of
`9.228` and `7.396` for the displayed paths, both marked `slack (MET)`.
These values belong to the specific constraints and paths in that
report; they should not be presented as interchangeable with the
post-route timing metric.

### Timing-constraint note

The observed `sta/sta.tcl` contains a 10 ns clock constraint, while
`pnr/config.json` was shown with `CLOCK_PERIOD` set to `3.5`. Because
the constraints differ, standalone STA and physical-design timing
results are not directly comparable. For a formal report, state which
constraint produced each result, and align the constraints if the
assignment requires a direct comparison.

## Limitations and Notes

-   Functional simulation verifies the tested vectors and the testbench
    checks; it is not a substitute for timing analysis or physical
    signoff.
-   Timing numbers depend on clock constraints, timing libraries,
    process/voltage/temperature corner, and whether the result is
    pre-route or post-route.
-   Area and wire-length values must be reported with the metric
    definitions and units used by the tool.
-   DRC/LVS pass messages apply to the configuration and run that
    produced them.
-   The README is documentation; the actual RTL, scripts, constraints,
    reports, and generated layout are the source of truth.
